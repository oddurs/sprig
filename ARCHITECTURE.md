# Architecture

This is a map of the repository for someone about to change it. It says where
things are and why they are there; the code says how. If you read one other
file, read [`spec/sprig.md`](spec/sprig.md): everything here serves it.

## Bird's-eye view

A Sprig plan is a folder of `.sprig` text files. Every tool answers the same
question: given those files and today's date, what does the plan say? What is
done, what is blocked and on what, who owns what, what is wrong.

```text
  files on disk ──► loader ──► Workspace ──resolve(today)──► Resolution ──► answers
  (CLI, LSP, MCP)  (reads)    (sprig-core: text in, no I/O)  trees,         next, check,
                                                              diagnostics   agenda, JSON…

  source text ──► edit::tick / set_mark / add / format ──► Change ──► written back
                  (sprig-core)                            new text + replacements
```

There is one implementation of the format, `sprig-core`, and every surface is
a thin shell around it: the `sprig` command, the language server, the MCP
server, the TUI and the website's playground (compiled to WebAssembly). Two
surfaces can never disagree about what a file means, because only one thing
decides (cairn 0040).

Reading is a pure function. A caller hands the core the text of each file and
a date; the core hands back trees and diagnostics. Writing is a pure function
too: the core takes source text and returns new source text plus the exact
replacements that produced it. Only the shells touch the filesystem.

## Code map

### `spec/`

The authority. `sprig.md` is the format, every rule numbered (§1 to §10).
`diagnostics.md` is the catalogue of problem codes, which are never reused.
`tools.md` is what a tool built on the format must do (T1 to T6).
`tree.schema.json` is the JSON shape of a resolved tree. The spec is CC0, so
anyone may implement it.

### `tests/conformance/`

The spec's evidence: 417 examples, each a folder with `main.sprig`, the rules
it demonstrates and the `expected.json` the core must produce. Edit examples
also carry an `after.sprig`, compared byte for byte. Any implementation can run
them; ours does in `crates/sprig-core/tests/conformance.rs`.

**Invariant:** every numbered rule in the spec has an example. A test fails
when one does not, and the README's coverage report is regenerated by that
same test.

### `crates/sprig-core`

The parser, the resolver and the edit API. No I/O.

- `syntax.rs` reads one file into a tree (§1 to §3). It looks at nothing but
  that file's text: no other file, no date. `lex` gives the line kinds an
  editor highlights.
- `token.rs` reads what an item's line says besides its text (§4): `@people`,
  `^anchors`, `after:` waits, `due:`, `est:`, `#tags` and other fields.
- `date.rs` is civil dates, hand-rolled, so the core depends on no date
  library and every date rule in §10 is ours to test.
- `workspace.rs` is many files as one plan: grafts (§8), status and progress
  (§5), people (§6) and blocking (§7). `Workspace::wanted` tells a loader which
  files a plan names that it has not been given yet, so a loader reads only
  what the plan reaches.
- `diagnostic.rs` holds every problem's `Code`, generated from one table so
  the code, its severity and its summary cannot drift apart.
- `edit.rs` changes files: tick, mark, add, answer, format. See *Edits* below.
- `next.rs`, `agenda.rs`, `query.rs`, `refs.rs`, `graph.rs`, `export.rs`,
  `import.rs` and `json.rs` are the questions a resolved plan answers, and
  the other formats it goes to and comes from.

**Invariant:** the core never reads the filesystem, the environment, the
network or the clock. `scripts/task lint` greps for it, crudely and on
purpose. This is what makes an answer the same on every machine, and what lets
the same code run in a browser.

**Invariant:** user input never panics. Every problem in a file becomes a
`Diagnostic` with a stable code. `crates/sprig-core/tests/robustness.rs`
(property tests) and two `cargo-fuzz` targets in `crates/sprig-core/fuzz/`
hold it, and CI fuzzes each for a minute.

### `crates/sprig-cli`

The `sprig` binary. `main.rs` dispatches; `args.rs` is the command line, built
with clap, and the only file in the repository allowed to read the clock.
`load.rs` turns paths into a `Workspace`, reading only what the plan names.

- `views.rs`: `next`, `check`, `tree`, `why`, `status`, the commands that read
  and print.
- `write.rs` and `verbs.rs`: `fmt`, `tick`, `mark`, `answer`, `add` and `edit`,
  each a core edit applied to a file.
- `data.rs`: `find`, `agenda`, `graph`, `export` and `import`.
- `out.rs`: how output looks, in one place: widths, colour, and `--plain`,
  whose tab-separated columns are a promise (`docs/stability.md`).
- `mcp.rs`: `sprig mcp`, the plans served to coding agents over the Model
  Context Protocol. It reads afresh on every call, because a person, an editor
  and an agent can all change a file between calls, and the file is the truth.
- `agent.rs`: `sprig agent`, the instructions that tell an agent how to use
  this.
- `tui/`: `sprig tui`. `app.rs` is the state and what each key does, pure and
  tested without a terminal; `ui.rs` draws a frame; `mod.rs` owns the terminal
  and the file watcher. `--screenshot` renders a frame as text, which is how
  the TUI is tested and how the guide shows it.

### `crates/sprig-lsp`

The language server, built the way rust-analyzer is: `lsp-server` and
`lsp-types`, one thread, no async runtime. A change marks the workspace stale,
and it is resolved again once the message queue is empty, so a burst of
keystrokes costs one resolution. Diagnostics are republished for every file
whose problems changed, including files nobody edited (cairn 0049). `pos.rs`
converts the core's byte offsets to LSP's UTF-16 positions.

### `crates/sprig-wasm`

`sprig-core` for the browser. One call takes a JSON request and returns a JSON
answer, so the site needs no bindings generator. Offsets are in UTF-16 code
units, because that is how JavaScript indexes a string.

### `editors/`

- `sprig.tmLanguage.json`: the TextMate grammar, for VS Code.
  `editors/tests/textmate/` snapshots how it scopes three files.
- `tree-sitter-sprig/`: the tree-sitter grammar, for Neovim, Helix and Zed.
  `editors/tree-sitter-sprig/tests/agrees_with_core.rs` checks that every line of every conformance
  example gets the same kind and the same tokens as it does from the core.
- `vscode/`: the extension, which bundles `sprig lsp`.
- `neovim/`: a Lua config and its test.

**Invariant:** the grammars only highlight. What a file means is decided by
the core, and the agreement test catches a grammar that drifts.

### `site/`

The website, built with Astro. `site/scripts/sync.mjs` copies the spec, the
changelog, the roadmap, the decisions and the reference pages into the site
at build time, from the repository and from the `sprig` binary itself, so a
page cannot drift from its source. The playground runs `sprig-wasm`, and
shows what `sprig check` would say as you type.

The build then checks the built pages in headless Chrome, with no browser
driver: every value is a design token (`lint-tokens.mjs`), every colour pair
has its contrast (`contrast.mjs`), every link resolves (`check.mjs`), axe finds
nothing in either theme (`a11y.mjs`), and nothing scrolls sideways or is too
small to tap at a phone's width (`mobile.mjs`). `playground.mjs` drives the
playground wide and narrow. `harness.mjs` is the server and the Chrome they
share.

### `action/`

The GitHub Action: it checks plans and writes a summary of what a pull
request did to them. This repository's CI runs it on its own examples.

### `cairn/` and `ROADMAP.md`

The backlog, one Markdown file per item, managed by
[cairn](https://oddurs.github.io/cairn). Items of type `decision` are the
format's settled arguments. `ROADMAP.md` is generated from them.

### `rfcs/` and `docs/`

How the spec changes (`rfcs/README.md`), and what will not change under you
after 1.0, each promise with the test that holds it (`docs/stability.md`).

### `scripts/`

`task` is the one seam all automation goes through: CI, the hooks and people
run the same targets, so they cannot disagree. `agent` drives the
item-branch-worktree-pull-request loop. `setup` installs the hooks.

## Cross-cutting concerns

### Edits

A Sprig file is line-oriented: every byte belongs to exactly one line. So the
source text is already the lossless layer that format-preserving editors build
a concrete syntax tree to keep. An edit is a set of replacements of whole or
partial lines, located by the parser's spans, and every byte it does not name
is copied through: indentation style, line endings, a BOM, comments and blank
lines survive by construction (cairn 0042).

**Invariant:** anything that writes a file goes through `sprig_core::edit`:
the CLI's verbs, the TUI, the language server's quick fixes and MCP. The
`edits` fuzz target checks that an edit changes nothing it did not name.

The shells add one rule on top: a write is refused if the file changed since
it was read. The TUI compares the line it showed, and MCP refuses a write that
would add an error `sprig check` reports.

### Grafts are untrusted

Plans arrive from repositories nobody has read. A graft or reference path that
would leave the workspace root is refused with a diagnostic, in the core,
before any loader is asked for the file. The loaders read nothing outside the
root either. See [`SECURITY.md`](SECURITY.md).

### The file is the truth

Progress, estimates, blockers and settled status are computed every time and
never written into a file. The computed layer may add hints, but it never
contradicts what the text says.

### Dates

Today's date is a parameter everywhere. The CLI takes it from `--today`, from
`SPRIG_TODAY`, or from the clock in `args.rs`. Tests pin it, so a snapshot
does not change at midnight.

### Testing

| What | Where |
| --- | --- |
| The format | `tests/conformance/`, run by `crates/sprig-core/tests/conformance.rs` |
| The examples in the spec's text | `crates/sprig-core/tests/spec_examples.rs` |
| Never panics, edits preserve bytes | `crates/sprig-core/tests/robustness.rs` and `editing.rs` (proptest), `crates/sprig-core/fuzz/` |
| The public API is documented | `crates/sprig-core/tests/api.rs`, and `cargo doc` with warnings denied |
| The command line | `crates/sprig-cli/tests/`, with snapshots in `crates/sprig-cli/tests/snapshots/` (`SPRIG_BLESS=1` rewrites them) |
| The README, the tutorial and the shell guide run as written | `crates/sprig-cli/tests/readme.rs` and `guide.rs` |
| The stability policy names real tests | `crates/sprig-cli/tests/docs.rs` |
| The language server | `crates/sprig-lsp/tests/lsp.rs` |
| Performance | `scripts/task perf`, against `crates/sprig-core/benches/baseline.json` |

Name a test after the behaviour it protects, not after the function it calls.
