The Sprig command line

A toolbelt, not an app.

One binary. Small verbs that read a folder of plans and answer one question each, in text a person can read and a pipe can parse. The TUI is the same verbs on one screen.

One binary · no daemon · no config · no network · a 30 ms budget

The rules it lives by

These decide every command below. Where a feature would break one, the feature loses.

  • x
    Every command is a verb

    Nouns are files and refs. sprig next, sprig why, sprig tick. No subcommand trees, no modes to remember.

  • >
    Three kinds of output

    Readable on a terminal, stable tab-separated text with --plain, the full tree with --json. Output only changes shape when you ask it to.

  • ~
    Exit codes mean something

    0 fine, 1 the answer is "no" (findings, nothing ready), 2 you asked wrong. Scripts branch on them.

  • +
    A write touches one line

    tick, add and answer change the bytes they mean to and nothing else, so git diff shows exactly what happened.

  • #
    Colour is optional

    The mark is the status, so NO_COLOR loses nothing. Colour follows the marks and nothing else.

  • ?
    Answers are reproducible

    --today 2026-10-01 pins the date, so any output can be tested, diffed and filed in a bug report.

  • =
    No prompts in a pipe

    Interactive only when stdin and stdout are terminals. No pager unless $PAGER is asked for with -p.

  • /
    Nothing runs in the background

    No daemon, no index, no cache to go stale. Parsing a hundred files is fast enough to do every time.

Pointing at an item from the shell

Every command that acts on one item takes a ref. The forms go from exact to forgiving, and an ambiguous ref lists its candidates and exits 2 instead of guessing.

RefMeansExample
^signedAn anchor, searched across the foldersprig tick ^signed
lease^signedAn anchor in one filesprig why lease^signed
lease.sprig:7A line, the way compilers and editors say itsprig tick lease.sprig:7
"grease trap"Words from the item's text, if they match exactly one itemsprig answer "grease trap" "Landlord pays"
-Refs on stdin, one per line, from another commandsprig next --plain | cut -f1 | sprig tick -

The toolbelt

Every screen below is computed live from the example bakery plans by the draft reference parser, with dates relative to today. The check and fmt examples have mistakes planted in them. The diagnostic codes are placeholders.

Read

answer a question, change nothing
sprig next [@who] [--limit N]v0.1

What can be done now: open, unblocked work, in progress first, then priority, then due date. The command you'll type most.

sprig status [--oneline]new

One screen for the whole folder: progress per file, what's waiting, what's late. --oneline is sized for a prompt or a tmux status bar.

sprig tree [file] [--depth N] [--hide-done]v0.2

The plan as Sprig reads it, grafts expanded, progress rolled up, with what each item waits on.

sprig why <ref>new

Why something is blocked, all the way down. The dependency chain, with the file and line of every link in it.

sprig agenda [--days N]new

Dated work by day, across every file, recurring items included. The calendar view without a calendar.

Check

fail loudly, fix nothing silently
sprig check [paths] [--strict]v0.1

Broken links, loops and unknown anchors, as file:line:col so editors and CI jump straight there. Exits 1 on any error.

sprig fmt [--check]v0.2

Two spaces per level, typed dates expanded to ISO, trailing space gone. Idempotent; --check lists files that would change and exits 1.

Write

one line at a time
  • sprig tick <ref>…v0.2

    Mark done, or reopen if done. A recurring item moves its due date instead. Prints the changed line.

  • sprig mark <ref> <- ~ x / >>new

    Set any status. sprig mark ^logo ~ says you've started.

  • sprig add "text" --under <ref>new

    Append an item under a parent, indented correctly, with tokens parsed from the text.

  • sprig answer <ref> "text"new

    Write the = line that settles a question, and show what it unblocked.

  • sprig edit <ref>new

    Open $EDITOR at the item's line (+7 lease.sprig), for anything the verbs don't cover.

  • sprig find <query>new

    Search by text and by @who, #tag, is:blocked, is:ask, due:<fri. Read-only, but here because its output feeds the writers.

Connect

other tools, other formats
  • sprig export --json | --ics | --csvv0.3

    The resolved tree as data, due dates as a calendar feed.

  • sprig import checklists.mdv0.3

    Markdown checkboxes and todo.txt in, a Sprig file out.

  • sprig graph [--format dot|mermaid]new

    The dependency graph, for Graphviz or a README.

  • sprig mcp · sprig agentv0.3

    Serve the plans to coding agents; print the instructions they need.

  • sprig completions <shell> · sprig mannew

    Completion that knows your anchors and people; a real man page.

  • sprig tuinew

    Everything above on one screen. Below.

The TUI

Three views of the same folder, vim keys, and writes that go through the same one-line edits as the verbs. It reloads when a file changes on disk, so an editor, an agent and the TUI can all be open at once. This one works: click it, then use the keys.

  • j kmove down and up
  • h lfold and unfold a branch
  • xtick: done, or reopen
  • ~mark as doing
  • 1 2 3tree, next up, agenda
  • /filter by text; Esc clears
  • eopen $EDITOR at the line
  • a Aadd a sibling, add a child
  • uundo this session's last write
  • ?help
  • qquit

e, a, u and q belong to the real thing; here they say what they'd do. Ticks change the demo's copy of the plans, not anything on disk.

Colour is a courtesy

The same sprig tree, with colour and with NO_COLOR=1. Nothing is lost, because in Sprig the character is the status. Colour only ever repeats what the mark already says.

Pipes

The payoff of plain output and meaningful exit codes: Sprig composes with the tools already on the machine, and needs no plugin system.

Pick and tick with fzf

Choose from what's ready; the first column of --plain is always a ref.

Your next task in the prompt

A Starship custom module, or any prompt that runs a command.

Gate a commit

A pre-commit hook that blocks broken plans, and only reads the files that changed.

What's everyone waiting on?

The resolved tree as JSON, queried with jq.

Deadlines in any calendar

Regenerate on a timer; calendars subscribe to the file.

The graph as a picture

Graphviz does the drawing.

What it will not do

Each of these was tempting. Each would make Sprig something you have to run, configure or trust, instead of a tool you pick up.

  • No daemon or index. Reading the files every time is fast enough, and nothing goes stale.
  • No config file. Flags and environment variables only. A plan should read the same on every machine.
  • No plugins. Pipes are the plugin system. JSON out covers the rest.
  • No network, no accounts, no telemetry. Sync is git's job, or Syncthing's.
  • No interactive wizards. sprig add takes its text as an argument; the TUI is the interactive surface.
  • No second parser. The CLI, the TUI, the MCP server and the website all use the one Rust core.

How it gets built, and when

Commands marked v0.x are already items in the roadmap. Those marked new are filed as items 0117 to 0135, with the TUI under a new v0.4 milestone (0116).
